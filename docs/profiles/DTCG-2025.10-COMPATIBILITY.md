# DTCG 2025.10 compatibility profile

## Outcome

The current reference Web token document is a:

> **DTCG 2025.10-compatible closed reference profile**

It is not a complete DTCG parser, a complete DTCG resolver, a new token-file standard, or the
generic token policy of DESEN.

DESEN continues to carry only token references. Token storage and resolution remain host-owned, as
required by DESEN 0.1.0 §14.4. The current reference package happens to use one valid, deliberately
narrow DTCG document and projects it to 26 Web CSS custom properties. Future Web, iOS, Android, or
other hosts may use different target adapters without changing the DESEN document model.

The executable audit receipt is
`docs/proof/artifacts/sc-01-dtcg-compatibility.json`
(`sha256:1df806e0b56d66e27558bbc2bb2f17e0e261b0103c90ed2658ad1eba4c3bdbc6`).
Its 16 focused tests audit the 26-token built reference document, 14 unsupported feature families,
16 exact valid-but-unsupported fixtures, and seven exact negative fixtures.

## DESEN ownership boundary

DESEN 0.1.0 intentionally does not define a token store:

```json
{ "$token": "color.action.primary" }
```

The host token provider resolves that opaque token name. The receiving Catalog schema determines
whether the resolved value has the type required by the target capability. DTCG can standardize
the host's token exchange/storage document without becoming part of the DESEN Source or Bundle
schema.

Consequences:

- no DTCG fields are added to the frozen DESEN schemas;
- no DTCG document is embedded in a production Bundle by this profile;
- M04-T03 consumes a host token port rather than owning a token database;
- CSS custom-property naming remains a Web adapter concern; and
- future native adapters can project the same token identity to native values without importing
  React, DOM, CSS, or browser APIs into `runtime-core`.

## Supported types and target mapping

### Color

The profile accepts:

```json
{
  "$type": "color",
  "$value": {
    "colorSpace": "srgb",
    "components": [0.1137254902, 0.3058823529, 0.8470588235],
    "alpha": 1,
    "hex": "#1d4ed8"
  }
}
```

`alpha` and `hex` are both valid DTCG Color members, but DTCG makes them optional in forms where
the profile requires them. Requiring both gives the current Web adapter a deterministic checked CSS
fallback. It must not be generalized into a claim that DTCG itself requires those members.

Other DTCG color spaces, `none` components, and valid colors without the local fallback fields are
classified as `UNSUPPORTED_DTCG_FEATURE`, not `INVALID_DTCG`.

### Dimension

The profile accepts `px` and `rem` dimensions exactly as defined by DTCG 2025.10:

```json
{
  "$type": "dimension",
  "$value": { "value": 1, "unit": "rem" }
}
```

The Web adapter serializes the pair to a CSS dimension. A future iOS or Android adapter must define
its own conversion and any loss policy rather than reusing CSS strings as a platform-neutral
value.

### Aliases

The current parser accepts a whole-token curly alias only when its path contains at least two
segments:

```json
{ "$value": "{color.action.primary}" }
```

DTCG also permits a valid one-segment root alias such as `{primary}`. The local parser currently
rejects that form, so SC-01 records it as a compatibility gap. This checkpoint does not widen the
public provider or silently reinterpret it.

DTCG also permits an alias with no own or inherited `$type` to derive its effective type from the
resolved target. The current local provider requires a type before resolving the alias, so that
valid form is recorded as unsupported rather than invalid.

JSON Pointer `$ref`, property-level references, `$root`, and `$extends` are also outside the
current closed profile.

## Valid DTCG features intentionally unsupported

The audit keeps these separate from malformed DTCG data:

| Fixture family                                          | DTCG status            | Local classification       |
| ------------------------------------------------------- | ---------------------- | -------------------------- |
| One-segment root alias `{primary}`                      | Valid                  | `UNSUPPORTED_DTCG_FEATURE` |
| Alias type inherited only from its resolved target      | Valid                  | `UNSUPPORTED_DTCG_FEATURE` |
| JSON Pointer `$ref`                                     | Valid                  | `UNSUPPORTED_DTCG_FEATURE` |
| Property-level JSON Pointer reference                   | Valid                  | `UNSUPPORTED_DTCG_FEATURE` |
| `$root` token in a group                                | Valid                  | `UNSUPPORTED_DTCG_FEATURE` |
| `$extends` group inheritance                            | Valid                  | `UNSUPPORTED_DTCG_FEATURE` |
| Empty group                                             | Valid                  | `UNSUPPORTED_DTCG_FEATURE` |
| `$extensions` metadata                                  | Valid                  | `UNSUPPORTED_DTCG_FEATURE` |
| `$deprecated` metadata                                  | Valid                  | `UNSUPPORTED_DTCG_FEATURE` |
| Other types such as `number` or `typography`            | Valid                  | `UNSUPPORTED_DTCG_FEATURE` |
| Other color spaces such as Display P3 or OKLCH          | Valid                  | `UNSUPPORTED_DTCG_FEATURE` |
| Color component value `none`                            | Valid                  | `UNSUPPORTED_DTCG_FEATURE` |
| Valid opaque color without local `alpha`/`hex` fallback | Valid                  | `UNSUPPORTED_DTCG_FEATURE` |
| Resolver theme, mode, set or modifier document          | Valid Resolver feature | `UNSUPPORTED_DTCG_FEATURE` |

The executable audit classifies only its exact reviewed malformed fixtures as `INVALID_DTCG`.
Those fixtures cover malformed token/group shapes, references, cycles, values, and Resolver
structure. The proof-only helper is not a general DTCG validator, so its outcome for an arbitrary
document outside the listed matrix is not a standards-validity decision.

This distinction matters for future import UX: “valid standard feature not supported here” is not
the same statement as “invalid token document.”

## Unknown metadata and round-trip policy

The current closed provider rejects unknown group/token members. That is correct for a fixed
runtime-owned reference document. It is not sufficient for a general Desen App DTCG importer:

- a future editable importer must preserve unknown `$extensions` data through round-trip;
- it must not strip `$deprecated`, `$root`, `$extends`, or unsupported token types;
- it must show an explicit unsupported-feature diagnostic before target projection; and
- it must keep the platform-neutral token document separate from Web/iOS/Android target adapters.

No general importer or exporter is added by SC-01.

## Future work boundary

The following work is recorded without moving it into M04-T03:

1. Keep M04's token API as a host-owned resolution port.
2. When general import/export enters scope, expose a pure document-to-provider adapter rather than
   coupling parsing to the fixed module constant.
3. Distinguish `INVALID_DTCG` from `UNSUPPORTED_DTCG_FEATURE` in that adapter.
4. Consider one-segment root aliases and target-derived alias types as the smallest compatibility
   improvements.
5. Preserve unknown DTCG extension data in any editable round-trip.
6. Implement theme/mode behavior as a separate DTCG Resolver 2025.10 adapter.
7. Test independent Web, iOS and Android projections instead of treating CSS as the canonical
   token value.

Any public parser/resolver claim requires its own task, complete conformance fixtures, resource
limits, compatibility matrix, and ADR.

## Limitations

- The current provider accepts one in-package constant, not caller-supplied DTCG files.
- The audit does not claim complete Format, Color, or Resolver conformance.
- The 26 CSS properties prove only the current reference Web component needs.
- DESEN token references do not identify a DTCG file, mode, theme, set, resolver, or network
  location.
- This checkpoint changes no frozen protocol byte and no public token-provider API.
